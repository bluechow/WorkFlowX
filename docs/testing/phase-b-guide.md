## 2. 测试流程（建议按序执行，每步产物落盘）

### 第 1 步：建立测试计划
把 `checklist.md`（同目录）复制一份为 `my-checklist.md`，作为你的功能遍历主清单。
先通读一遍，标注你打算重点测的模块（建议：Issue 全生命周期、看板、权限边界、Excel、报告页）。

### 第 2 步：探索式功能测试
- 按 checklist 逐模块遍历：**正常流 → 边界值 → 异常流**（如标题 200 字边界、特殊字符、
  重复提交、刷新/回退后状态、双开浏览器并发操作同一 Issue）。
- 权限专项：用 `demo_pm`（MEMBER，无管理权限）和 `demo_admin` 各操作一遍，
  对比按钮显隐与拒绝行为；直接改 URL 访问无权限页面。
- 每发现一个异常 → 立即填缺陷单（§3 模板），**先复现一遍再记录**。

### 第 3 步：接口测试（自动化）
- 现有套件：`tests/api/`（pytest + httpx，179 条黑盒用例）。运行：
  ```bash
  python -m pytest tests/ -v
  ```
- 你的任务：**模仿 `tests/api/test_issue_api.py` 的结构**，为你探索中发现的可自动化场景
  补写用例（命名 `test_<模块>_api.py`）。铁律：
  - 全部走真实 HTTP，数据库只用于清理（conftest.py 已内置）；
  - 测试用户一律 `api_test_` 前缀（工厂 fixture 已封装）；
  - 断言状态码 + 业务字段，不 sleep。

### 第 4 步：性能测试（可选加分）
方案见 `docs/testing/performance-testing.md`。建议抓两个核心接口（登录、Issue 列表）
做阶梯并发，记录 P95/吞吐/错误率，落一份 `docs/testing/perf-result-phaseb.md`。

### 第 5 步：测试报告
全部遍历完成后，汇总为 `docs/testing/phase-b-report.md`：
测试范围、方法、用例统计、缺陷分级统计、典型缺陷分析（挑 3~5 个讲根因）、结论。

## 3. 缺陷单模板

在 `docs/testing/bug-log.md`（自建）中按编号记录，格式：

```markdown
## BUG-<序号> <一句话标题>
- 级别：P0 致命 / P1 严重 / P2 一般 / P3 轻微 / P4 建议
- 模块：登录 / 组织 / 项目 / Issue / 看板 / 抽屉 / 个人中心 / 会话 / 用例库 / 计划 / 报告 / Dashboard
- 环境：localhost:8081（v1.2.0），Chrome，账号 demo_admin
- 复现步骤：
  1. …
  2. …
- 预期：…
- 实际：…
- 证据：截图路径（建议存 docs/testing/bugs/ 下）
- 备注：首次发现于第 N 轮遍历
```

分级参考：**P0** 主流程阻塞/数据丢失；**P1** 核心功能错误/权限越界；**P2** 非主流程错误
有绕过办法；**P3** 文案/样式/体验；**P4** 改进建议。

## 4. 提交约定（复现→修复的对应关系）

- 每个确认的缺陷先登记 bug-log，**不要急着让我修**——攒到一批后统一排期；
- 修复提交信息格式：`fix(<模块>): BUG-012 <一句话>`，答辩时提交历史就是缺陷闭环证据；
- 你自己发现的缺陷由**你决定**修不修、什么优先级——这是测试负责人的权力。
